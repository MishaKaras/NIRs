## Что должно получиться по каждой задаче

### Задача 1 — модель и алгоритмы (`1chap.typ`)

НИР №1 дал **метод** на содержательном уровне. Здесь его нужно **формализовать**, а не пересказывать:
- **формальная модель:**
  - инфраструктура как множество уровней и объектов (узел, под, контейнер, образ);
  - артефакт как кортеж (тип, уровень, источник, волатильность, provenance, хеш);
  - класс инцидента → профиль как отображение в множество артефактов;
  - функция приоритета / порядок по волатильности;
  - модель chain of custody (журнал операций);
  - модель корреляции (граф или отношение идентификаторов `PID ↔ cgroup-ID ↔ container_id ↔ pod_uid ↔ namespace ↔ node`);
  - модель события timeline;
- **алгоритмы** (псевдокод + блок-схема/диаграмма деятельности):
  - формирование набора артефактов по дескриптору и профилю;
  - построение приоритизированной очереди;
  - сбор единичного артефакта с фиксацией хеша, provenance и custody, обработка отказов;
  - верификация целостности;
  - нормализация;
  - корреляция;
  - построение timeline;
  - поиск IoC по правилам;
  - формирование отчёта.

  По возможности оценить сложность и обозначить свойства (завершимость, детерминированность порядка сбора);
- **диаграммы (UML):** состояний артефакта (жизненный цикл: запланирован → собран → захеширован → проверен → проанализирован / ошибка), классов (модель данных), деятельности или последовательности для ключевых алгоритмов. Схемы НИР №1 (`Part_1_trash/drawio/5_final/`) использовать как основу, но не дублировать в тексте.

### Задача 2 — спецификация требований и перечень артефактов (`2chap.typ`)

- **спецификация требований** на основе ФТ-1…8 и НФТ-1…6 из НИР №1, уточнённых до проверяемого вида. Ориентир структуры — ГОСТ 34.602-2020 (ТЗ на АС) и/или ISO/IEC/IEEE 29148. В неё входят:
  - назначение и границы системы;
  - роли пользователей и сценарии использования (use case);
  - функциональные требования с критериями приёмки;
  - нефункциональные требования с измеримыми показателями;
  - требования к входным и выходным данным (дескриптор, манифест, формат отчёта);
  - ограничения и допущения;
  - трассировка «ФТ/НФТ НИР №1 → требования спецификации»;
- **перечень собираемых прототипом артефактов** — таблица по пяти уровням. Для каждого артефакта:
  - источник (путь / команда / API);
  - формат;
  - волатильность и позиция в очереди;
  - необходимые привилегии;
  - класс(ы) инцидентов, для которых он нужен;
  - поддерживается ли прототипом (да / частично / нет, с обоснованием).

  Явно разделить «система в целом» и «прототип»: прототип реализует обоснованное подмножество.

### Задача 3 — технологический стек (`3chap.typ`)

Для каждого выбора: варианты → критерии (с весами, если уместно) → сравнительная таблица → обоснованный выбор. Кандидаты (уточнить при анализе):
- **язык реализации:** Go vs Python vs Rust (нативные клиенты Docker/containerd/K8s, статическая сборка, работа с eBPF, скорость разработки);
- **доступ к runtime:** Docker Engine API, containerd API / CRI (`crictl`), CRI-O;
- **доступ к оркестратору:** client-go / kubernetes-python, kubelet checkpoint API (`ContainerCheckpoint`), audit log;
- **снимок состояния:** CRIU, checkpointctl, Docker checkpoint;
- **источники уровня хоста/ядра:** `/proc`, auditd, eBPF-инструменты (Tetragon, Falco, Tracee, bpftrace);
- **сеть:** Hubble/Cilium, conntrack, tcpdump/pcap, CoreDNS-журналы;
- **образы:** Syft (SBOM), Trivy/Grype, crane/skopeo;
- **хранение артефактов и метаданных:** файловая структура + JSON/SQLite, MinIO/S3; хеширование (SHA-256); формат манифеста и отчёта (JSON, HTML), возможная совместимость с CASE/UCO;
- **анализ:** правила IoC (Sigma, YARA, собственный DSL), построение timeline (собственный модуль vs plaso/Timesketch);
- **испытательная среда для разработки:** Docker Desktop (установлен), kind/minikube/k3s для Kubernetes.

Ссылки на свежие (≥ 2021) научные работы использовать для обоснования критериев и выбора. Документацию инструментов — как электронные ресурсы.

### Задача 4 — программный прототип (`4chap.typ`)

- **Код прототипа** по умолчанию — в `../prototype/` в корне репозитория, а не в `Part_2/`: на этапе 3 этот же код проходит экспериментальную оценку. Если пользователь решит иначе, обновить этот пункт.
- Прототип реализует архитектуру из 6 компонентов НИР №1 (координатор, коллекторы пяти уровней, модуль целостности, хранилище, анализатор, сборщик отчёта) в объёме, определённом в задаче 2.
- **Обязательно:**
  - README с инструкцией запуска;
  - минимальные тесты (unit на модуль целостности, корреляцию, очередь);
  - демонстрационный прогон на локальном стенде (Docker + kind/minikube) хотя бы для одного-двух сценариев инцидентов;
  - пример манифеста и отчёта.
- **В главе:**
  - структура прототипа (диаграмма компонентов/пакетов, соответствие компонентам метода);
  - ключевые решения реализации;
  - короткие фрагменты кода;
  - интерфейс (CLI);
  - пример работы (скриншоты / фрагменты отчёта);
  - трассировка «требование спецификации → модуль прототипа → статус»;
  - ограничения прототипа.

  Полные листинги — в приложение.
- Экспериментальная оценка на наборе сценариев **не** входит в этот этап (это НИР №3). Здесь — только функциональная проверка работоспособности.

## Стенд и реализуемость (см. п. 5 методологии в корневом CLAUDE.md)

Целевой стенд для разработки и для НИР №3 — домашний:
- Linux-ВМ (Ubuntu LTS) на ПК пользователя с Docker Engine и одноузловым кластером k3s/kind (containerd);
- при необходимости второй узел-ВМ;
- Docker Desktop под Windows — только для быстрой отладки, потому что eBPF, auditd и CRIU требуют полноценного Linux-ядра.

Следствия для задач 1–3:
- модель и алгоритмы не должны требовать распределённой инфраструктуры. Последовательная очередь сбора на одном узле является базовым вариантом, параллельность — расширением;
- требования формулировать проверяемыми на таком стенде (числа, которые реально измерить);
- managed-кластеры (EKS/GKE/AKS), облачные журналы и снапшот etcd в managed-средах в прототип не входят, о них говорится только как об ограничениях;
- источники, требующие предварительного развёртывания (Tetragon/Falco, audit policy API-сервера, auditd-правила, CRIU), задаются как **предусловия**. Прототип проверяет их и при отсутствии фиксирует пропуск, а не падает.
